# 12｜SAC：Off-policy 對照實驗

> 參考來源：[Stable-Baselines3 SAC](https://stable-baselines3.readthedocs.io/en/master/modules/sac.html)、[SAC 論文（Haarnoja et al., 2018）](https://arxiv.org/abs/1801.01290)
>
> 擷取日期：2026-09-09
>
> 相依套件：`pip install gymnasium stable-baselines3`（實測 sb3 2.9.0、torch 2.14.0，Linux CPU）

## 學習目標

- 了解 off-policy（SAC）與 on-policy（PPO）的差異與取捨
- 學會重用 Gymnasium Env 直接替換演算法
- 認識 CPU 訓練的效能陷阱（`train_freq` / `gradient_steps`）

## 前置知識

- [09｜Gymnasium + PPO](04-ppo-gymnasium.md) — 本章直接重用其中的 `SwingUpEnv`

## SAC 與 PPO 的差異

| | PPO（09 章） | SAC（本章） |
| --- | --- | --- |
| 類型 | on-policy | off-policy（有 replay buffer） |
| 資料利用 | 蒐集一批用過就丟 | 舊資料反覆回放學習 |
| 探索 | 策略本身的隨機性 | 隨機策略 + 熵（entropy）獎勵 |
| 每步成本 | 低（定期更新） | **高（預設每個 env step 都做梯度更新）** |
| 樣本效率 | 低 | 高（理論上） |

## 程式（`scripts/ex_rl_sac.py`）

環境完全重用，只換演算法：

```python
from ex_rl_ppo import SwingUpEnv   # 09 章的環境
from stable_baselines3 import SAC

model = SAC("MlpPolicy", env, learning_rate=3e-4,
            buffer_size=50_000, batch_size=256, seed=0,
            train_freq=(4, "step"), gradient_steps=1)
```

> ⚠️ **`train_freq` 的取捨比想像中不划算**：SAC 預設 `train_freq=1`，每收集一步就做一次
> 梯度更新。本章的 `scripts/ex_rl_sac.py` 把它改成 `(4, "step")`，理由是「CPU 上每步更新
> 太貴」—— 實測把這個理由推翻了。在閒置的 8 核機器上，一次梯度更新約 **1.4 ms**，
> `train_freq=1` 跑滿 60k 步只要 **84 秒**；改成 4 之後是 26 秒。省下的那一分鐘，代價是
> 完全學不起來（下一節的消融）。

## 實測結果（上）：本章原設定 — 60k 步沒學起來

> 測試環境：Linux（8 核共用主機）、Python 3.12.3、MuJoCo 3.13.0、sb3 2.9.0、
> torch 2.14.0（**CPU**）；開跑時 load average 0.09（機器閒置，牆鐘時間才有得比）。

```
訓練前評估: -1.9651
  3000 步後: -1.9968    24000 步後: -1.9953    45000 步後: -1.9974
  6000 步後: -1.9880    30000 步後: -1.9979    51000 步後: -1.9911
  9000 步後: -1.9974    36000 步後: -1.9974    54000 步後: -1.9348
 12000 步後: -1.9859    39000 步後: -1.9954    57000 步後: -1.9371
 18000 步後: -1.9965    42000 步後: -1.9995    60000 步後: -1.7635   耗時 37.7 秒
```

**60k 步內回報幾乎不動（≈ -2.0，完全躺平）。** 三件事可以先排除：

1. **不是環境或回報設計的問題**：同一個環境，PPO 在 150k 步收斂（09 章）、ARS 在 30 輪
   收斂（08 章）。
2. **不是訓練預算不夠**：60k 步對 SAC 這種 off-policy 演算法綽綽有餘 —— 下一節同樣 60k 步
   就收斂到 -0.22。
3. **不是 CPU 算力不夠**：整輪 60k 步只花了 **37.7 秒**。

> 這組數字跨機器會變。SAC 一輪要做上萬次梯度更新，換一台 CPU 就換一條 BLAS 向量化路徑，
> 最後幾位小數跟著挪 —— 同一份程式碼在本機得到的是 -1.9996／-1.99xx 這組。**負面結果要看
> 的是結論穩不穩，不是小數點後第四位**：每台機器、每個版本跑出來都是「沒離開躺平」。
> MuJoCo 3.12.0 與 3.13.0 在同一台機器上則給出逐位相同的結果。

## 那到底是什麼卡住了？掃 `train_freq` × `learning_rate`

既然算力不是瓶頸，就回頭看被砍掉的那個參數。`scripts/ex_rl_sac_ablation.py` 把
`train_freq` 與 `learning_rate` 各取兩個值跑滿 60k 步，四組全部在 CPU 上：

| `train_freq` | `learning_rate` | 耗時 | 最終回報 |
| --- | --- | --- | --- |
| 4（本章原設定） | 3e-4 | 26.3 秒 | **-1.82**（躺平） |
| 4 | 1e-3 | 26.0 秒 | -0.33 |
| 1 | 3e-4 | 81.8 秒 | **-0.22**（收斂） |
| 1（zoo 設定） | 1e-3 | 83.9 秒 | **-0.21**（收斂） |

**`train_freq` 才是主因。** 只放開它、學習率完全不動，就從 -1.82 跳到 -0.22；反過來只調高
學習率、`train_freq` 維持 4，只走到 -0.33（有進步但沒收斂）。代價是 26 秒變 82 秒 ——
**用一分鐘換一個學得起來的策略。**

原始資料在 [runs/rl_sac_ablation.csv](../../runs/rl_sac_ablation.csv)。

> 這裡的教訓不是「`train_freq` 要設 1」，而是**為了牆鐘時間砍掉的超參，要回頭驗它砍掉了
> 什麼**。當初砍它的理由是一個從沒量過的估計（「一步更新 0.15 秒」，實測 1.4 ms，高估了
> 一百倍），而那個估計直接決定了整章的結論。**先量再調**，順序反了就會拿錯誤的前提去
> 解釋正確的現象。

## 實測結果（下）：GPU 對照 — 收斂，但沒快多少

> 測試環境：RTX Pro 6000（CUDA）、torch 2.14.0+cu130；腳本 `scripts/ex_rl_sac_gpu.py`，zoo 風格超參（`train_freq=1`、`gradient_steps=1`、`lr=1e-3`、8 個平行環境），60k 步約 **4 分鐘**。

```
訓練前評估: -1.9651
  15000 步後: -1.9946    33000 步後: -0.2724    51000 步後: -0.2153
  18000 步後: -1.1558    39000 步後: -0.2557    57000 步後: -0.2098
  21000 步後: -0.5582    45000 步後: -0.2226    60000 步後: -0.2101
  ...
```

**約 18k 步開始脫離躺平、21k 步後快速收斂，最終 -0.21，成功學會 swing-up。** 訓練好的策略存為 `policies/swingup_sac_gpu.zip`（已收錄於 repo），本地 CPU 回放驗證同為 -0.2101。

**但 GPU 不是收斂的原因，`train_freq=1` 才是。** 同一台機器、同一時段、同樣 4 個平行環境
與同一組 zoo 超參，兩邊的 60k 步是：

| 裝置 | 耗時 | 最終回報 |
| --- | --- | --- |
| CPU（8 核） | 83.9 秒 | -0.2127 |
| GPU（RTX Pro 6000） | 68.5 秒 | -0.2012 |

**GPU 只快 1.2 倍。** 原因是這個任務的網路小得可憐（`MlpPolicy` 預設兩層 256），每次更新
的矩陣運算量填不滿 GPU，kernel launch 的固定開銷反而佔了大頭。**「RL 訓練要用 GPU」是一個
要看規模的說法** —— 觀測三維、動作一維、兩層 256 的網路，CPU 完全夠用；真正吃 GPU 的是
大批次、大網路，或是像 28 章那樣把幾千條 rollout 一起向量化的場景。

（兩邊最終值差在小數第三位，是裝置間浮點路徑不同造成的軌跡差異，兩組都收斂到同一個水準。
GPU 那一列在 [runs/rl_sac_ablation_gpu.csv](../../runs/rl_sac_ablation_gpu.csv)。）

[![三種演算法的學習曲線](../../runs/rl_curves.png)](../../runs/rl_curves.png)

右圖（前 80k 步）看得最清楚：SAC 在約 12k 步就跳離躺平區並收斂，ARS 走到 80k 步還在
-0.65。這就是 off-policy 的樣本效率 —— 代價是每一步都貴得多（每筆資料做一次完整的梯度
更新），但「貴」在這個規模也只是 1.4 ms，CPU 扛得住。曲線資料在
[runs/rl_sac_gpu_log.csv](../../runs/rl_sac_gpu_log.csv)。

### 重現驗證（2026-09-11）

同一支腳本在 RTX Pro 6000 Blackwell（vGPU，`torch 2.14.0+cu130`）上重跑，這次用 `N_ENVS=4`：

```
平行環境數 = 4
訓練前評估: -1.9651          51000 步後評估: -0.2016
  ...                        57000 步後評估: -0.2045
                             60000 步後評估: -0.2012      耗時 86 秒
```

三件事在這次重跑得到確認：

1. **訓練前評估 -1.9651 與原紀錄完全一致** — 環境、seed 與評估流程沒有隨版本漂移。
2. **同設定連跑兩次，每個檢查點的數字逐位相同** — 腳本的 `seed=0` 確實鎖住了整條訓練軌跡。
3. **權重跨裝置可攜**：把 GPU 訓練出的 `.zip` 帶回本機用 CPU 回放，評估值同為 -0.2012，
   與遠端 GPU 上的數字沒有誤差。

但**換掉 `N_ENVS` 就不是同一條軌跡了**：4 個環境收斂到 -0.2012、8 個環境是 -0.2101。
seed 固定的是隨機數列，不是取樣順序 — 平行環境數一變，資料進 replay buffer 的順序跟著變，
梯度更新看到的批次也就不同。**要比較兩次訓練，`N_ENVS` 必須一起對齊**，只對 seed 不夠。

腳本預設 `N_ENVS=8`；在共用主機上跑時用環境變數調低，別把別人的核心佔滿：

```bash
N_ENVS=4 python scripts/ex_rl_sac_gpu.py
```

> 這台 GPU 跑得動 PyTorch，卻跑不動 JAX/XLA（vGPU 不支援 CUDA VMM）。
> 症狀與判斷方式見 [28 章](08-mjx-gpu.md)。

## 除錯紀錄

1. **把「沒收斂」歸因給 CPU 太慢，結論整章都歪掉**。當初的推理是：每步更新太貴 → 砍
   `train_freq` → 更新量不足 → 學不起來 → 所以要 GPU。前兩步都沒量過：實測一次更新
   1.4 ms、`train_freq=1` 跑完 60k 步只要 84 秒，CPU 從頭到尾都夠用。**憑感覺下的效能
   判斷會一路傳染到結論**，而且因為每一步聽起來都合理，回頭很難發現。掃參數之前先把
   中間量測出來（同樣的教訓見 20 章的摩擦實驗）。
2. **18k 步內完全沒學到**：SAC 的熵探索在「從垂下盪起」這種需要特定行為序列的任務上，冷啟動比 PPO 慢；本任務需要更長的訓練預算。這不是 bug，是演算法特性 — 文件如實記錄收斂曲線。
3. **牆鐘時間在共用機器上量等於沒量**。同一支腳本在 load 50 的機器上跑要數小時、在閒置的
   機器上 38 秒。量效能之前先看 `uptime`，並把當下的 load average 記進文件。

| | ARS（08） | PPO（09） | SAC（12） |
